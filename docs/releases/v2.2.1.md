# GGBot v2.2.1：微信桥接健康链路可靠性升级

这个维护版本针对长期无人值守设备上偶发的 `wx_bot health failed 3 consecutive times` 告警，重构微信桥接与主应用之间的健康判断。重点是消除 UI 自动化竞争造成的假离线，同时保留对真实掉线的自动恢复能力。

## 根因与处理

旧版主应用每 5 秒请求一次 `/health`，该接口会主动执行 `IsOnline`、枚举监听窗口并读取聊天信息；微信桥接自身的连接监控和监听器巡检也会访问同一个 UI 自动化对象。消息发送、媒体处理或窗口巡检耗时较长时，这些探针会互相竞争，短暂超时最终被主应用累计成三次健康失败。

v2.2.1 将健康链路改为分层模型：

- 只有连接监控线程可以主动调用 `IsOnline`，避免多个周期任务并发探测微信 UI。
- `/health` 和 `/api/is_online` 只读取线程安全的缓存快照，不再执行窗口操作。
- UI 锁繁忙记为 `busy`，保留最近确认的在线状态；单次 `false` 或异常先记为 `suspect`。
- 连续三次失败才确认离线，连续两次成功才确认恢复，降低瞬时抖动的影响。
- 主应用分别记录桥接超时、请求错误、无效响应和微信离线，不再把所有异常压缩成同一个布尔值。
- 本机 `127.0.0.1` 桥接请求明确绕过 `HTTP_PROXY`、`HTTPS_PROXY` 等系统代理环境，避免本地流量被错误转发。

## 连接身份与监听器恢复

桥接进程现在公开 `service_instance_id`，每次成功创建微信对象都会增加 `connection_generation`，两者组成稳定的 `connection_id`。

主应用仅在 `connection_id` 真正变化时发布微信重连事件并同步监听器。若只是 `/health` 短暂超时后恢复，连接 ID 不变，因此不会重复重绑窗口。对尚未提供连接 ID 的旧桥接版本仍保留兼容行为。

## 运维诊断

新增 `GET /live`，它只检查微信桥接进程是否能够响应，不依赖微信登录、窗口或监听器。

`GET /health` 新增以下关键字段：

- `health_status`：`ok`、`degraded` 或 `unavailable`。
- `online_probe`：探针状态、连续失败/成功次数、耗时、最近错误、跳过原因和快照年龄。
- `service_instance_id`、`connection_generation`、`connection_id`：判断桥接或微信对象是否真正重建。
- `listeners`：使用巡检缓存返回期望监听、实际监听和缺失项。

长期通过 SSH 管理的机器应先确认桥接进程和主应用进程存在，再在目标 Windows 会话内依次检查：

```powershell
curl.exe http://127.0.0.1:5555/live
curl.exe http://127.0.0.1:5555/health
curl.exe http://127.0.0.1:8888/api/wechat/status
```

微信 UI 自动化仍依赖一个可用的 Windows 交互桌面；本次升级改善无人值守运行中的并发、误判和诊断，不改变这一底层要求。

## 升级说明

- 本版本不修改数据库结构、插件接口或配置格式。
- 更新代码后需要完整重启 GGBot，使微信桥接与主应用同时加载新协议。
- 微信桥接端口仍默认只监听 `127.0.0.1`，无需也不建议对公网开放。
