# 模型连接与版本策略

Web 控制台的 `/ai/models` 用于管理“模型连接”。一个连接由配置名称、供应商、服务端模型、凭据引用和可选运行参数组成；插件和任务路由只引用配置名称，因此可以在不修改插件的情况下替换实际模型。

## 推荐录入流程

1. 选择 OpenAI、Anthropic、Gemini、DeepSeek、OpenRouter 或本地 Codex 等常用接入方式。
2. 从当前进程的 LiteLLM 模型目录中搜索模型。目录没有收录时可直接输入完整模型名。
3. 在唯一的“API Key”输入框粘贴供应商密钥。每个模型会自动生成独立凭据，允许同一供应商使用不同 Key；真实密钥保存在本机数据库，模型配置文件只记录 `env::...` 引用。编辑时留空会保留原值。
4. 使用“保存并测试”确认认证、地址和模型名都可用，再到“任务路由”分配主模型和备用模型。

自定义 OpenAI 兼容服务选择“自定义接口”，填写服务端返回的模型名和完整 API 地址。接口无需认证时，API Key 留空即可。

## 模型目录不是白名单

目录来自当前运行进程中的 LiteLLM `models_by_provider` 和模型成本/能力表，只负责辅助填写，不限制可保存的模型：

- 已有供应商发布新模型时，可以直接输入模型名。界面会显式保存供应商标识，避免仅因成本表尚未收录就无法识别供应商。
- 目录缺失的上下文窗口、最大输出、图片和搜索能力可以在“高级参数”中手动补充。
- OpenAI 兼容网关使用 `custom_openai` 适配器，不要求其私有模型出现在 LiteLLM 公共目录中。
- 新模型协议、全新认证方式或供应商 API 发生不兼容变化时，才需要升级 LiteLLM。

项目启动时可能由 LiteLLM 刷新模型成本与能力数据；离线时会继续使用随已安装版本提供的数据。元数据更新不能替代供应商适配器升级。

## LiteLLM 升级策略

不要在应用启动时自动执行 `pip install --upgrade`。自动升级会让部署不可复现，并可能在无人值守启动时引入调用、计费或回退行为变化。

建议使用显式升级流程：

1. 控制台模型选择器底部确认当前 LiteLLM 版本。
2. 在独立开发环境更新到计划版本，并固定或记录验证过的版本。
3. 运行模型配置、能力路由和关键插件测试。
4. 至少测试一个官方供应商、一个 OpenAI 兼容接口、本地 Codex，以及主模型失败后的备用模型。
5. 验证通过后再更新项目依赖并发布。

如果后续需要更新提醒，推荐增加管理员主动触发的“检查更新”，或在 CI/依赖机器人中创建升级 PR；检查结果只提示，不在生产进程中安装包。

## 分享前检查

- 模型卡片应显示“API Key 已就绪”或“本地调用”，避免把真实密钥直接写入模型配置。
- `.env.example` 只列变量名与用途，不填写真实值。
- 不提交 `data/llm_models.json` 中的直接密钥、自定义地址内嵌账号密码或调用历史。
- 为每个关键任务配置可用的主模型，并按需要设置不同供应商的备用模型。
- 在一台没有个人环境文件的新机器上走一遍首次配置流程。
